# LLM-structured

**AI-обработка входящих заявок на железнодорожную перевозку зерновых грузов**

Прототип системы, которая принимает заявку клиента в свободной форме — текст сообщения, email или документ — и преобразует её в структурированные данные, необходимые для дальнейшего создания сделки.

Основной принцип проекта: **не додумывать данные, которых нет в заявке**.

Система использует комбинацию детерминированного rule-based извлечения и опционального LLM fallback. Каждое извлечённое значение сопровождается evidence — фрагментом исходного текста, на основании которого оно было получено.

Rule-based extraction является первым уровнем системы по нескольким причинам:

1. **Контролируемость.** Regex и словари не могут самостоятельно придумать название станции или компании в отличии от галлюцинаций llm.
2. **Explainability.** Для каждого результата можно показать исходный фрагмент текста (`evidence`).
3. **Детерминированность.** Один и тот же вход даёт одинаковый результат.
4. **Работа без API.** Базовый pipeline не требует LLM API key.
5. **Контроль hallucinations.** LLM используется только как дополнительный источник информации.

LLM-pass предназначен прежде всего для случаев, когда свободная формулировка заявки не покрывается имеющимися правилами и словарями.

## Защита от hallucination

LLM не является единственным источником истины.
LLM должен возвращать для каждого значения:

```json
{
  "value": "...",
  "evidence": "...",
  "note": "..."
}
```

Перед принятием результата система проверяет, что `evidence` действительно присутствует в исходном тексте.
Если модель вернула значение, для которого невозможно найти соответствующий фрагмент исходного сообщения, значение отбрасывается.
Таким образом, генеративная модель используется для **извлечения**, но не получает права произвольно добавлять информацию в заявку.

---

## Разрешение конфликтов

Если одновременно доступны результаты rule-based extractor и LLM, они проходят через `resolver`.

Основные правила:

* если rule-based extractor обнаружил неоднозначность — итог остаётся `ambiguous`;
* если оба extractor нашли одинаковое значение после нормализации — используется rule-based результат;
* если оба нашли разные значения — поле становится `ambiguous`;
* если значение найдено только одним extractor — оно может быть принято;
* если ни один extractor ничего не нашёл — поле становится `missing`.

Для сравнения используются field-specific normalizers.

Например:

* числа нормализуются отдельно от текста;
* диапазоны объёма сравниваются с одиночными значениями;
* даты и периоды сравниваются как диапазоны или нормализованный текст;
* названия компаний, станций и грузов сравниваются с лемматизацией;
* условия погрузки сравниваются по ключевым концептам.

Это позволяет не считать автоматически ошибкой различия вроде `ООО "АгроТранс"` и `АгроТранс`.

## Возможности

Система извлекает следующие поля:

| Поле                 | Обязательное | Описание                    |
| -------------------- | -----------: | --------------------------- |
| `company`            |           Да | Компания-заказчик           |
| `station_from`       |           Да | Станция отправления         |
| `station_to`         |           Да | Станция назначения          |
| `cargo`              |           Да | Вид зернового груза         |
| `volume`             |           Да | Количество вагонов или тонн |
| `period`             |           Да | Период перевозки            |
| `loading_conditions` |          Нет | Условия погрузки/выгрузки   |
| `budget`             |          Нет | Бюджет или ставка           |

Для каждого поля система определяет один из трёх статусов:

* `found` — значение найдено и достаточно уверенно определено;
* `ambiguous` — информация присутствует, но её недостаточно для однозначного определения;
* `missing` — информация отсутствует.

Заявка считается полной только тогда, когда все обязательные поля имеют статус `found`.

## Поддерживаемые форматы

Входной файл автоматически преобразуется в единый plain-text представительный слой.

Поддерживаются:

* `.txt`
* `.eml`
* `.docx`
* `.pdf`
* `.xlsx`

### TXT

Читается непосредственно как UTF-8 текст.

### EML

Извлекаются:

* тема письма;
* plain-text body;
* HTML body, если plain-text отсутствует.

### DOCX

Извлекаются:

* обычные параграфы;
* содержимое таблиц.

### PDF

Извлекаются:

* текст страниц;
* таблицы.

### XLSX / XLSM

Последовательно читаются все worksheets и непустые значения строк.

После этого все форматы проходят один и тот же extraction pipeline.

## Rule-based extraction

Детерминированный extractor использует регулярные выражения, ключевые слова и доменные словари.

### Груз

Словарь содержит основные зерновые культуры и продукты:

* пшеница;
* ячмень;
* кукуруза;
* рожь;
* овёс;
* просо;
* гречиха;
* соя;
* подсолнечник;
* рапс;
* горох;
* жмых;
* шрот;
* отруби;
* комбикорм.

Обобщённое `зерно` считается неоднозначным, поскольку конкретная культура не определена.

### Станции

Используется доменный список железнодорожных станций, включая, например:

* Новороссийск;
* Новороссийск-Экспортный;
* Тамань;
* Ростов-на-Дону;
* Ставрополь;
* Краснодар;
* Волгоград;
* Самара;
* Оренбург;
* Курск;
* Воронеж;
* Омск;
* Барнаул;
* Новосибирск;
* Москва-Товарная;
* Санкт-Петербург-Товарный-Витебский.

Если в тексте явно указано направление (`от станции`, `до станции`, `на станцию` и т. п.), оно используется для определения origin/destination.

Если найдены две станции без явного указания направления, система не делает вид, что знает маршрут: станции помечаются как `ambiguous`.

## Формат результата

Пример результата:

```json
{
  "request_id": "sample_01_full",
  "is_complete": true,
  "fields": {
    "company": {
      "name": "company",
      "value": "ООО АгроТранс",
      "status": "found",
      "evidence": "ООО \"АгроТранс\"",
      "source": "rule_based",
      "confidence": 0.9,
      "note": null
    },
    "station_from": {
      "name": "station_from",
      "value": "Ставрополь",
      "status": "found",
      "evidence": "...",
      "source": "rule_based",
      "confidence": 0.85,
      "note": null
    }
  },
  "clarifying_questions": []
}
```

Для неполной заявки система дополнительно формирует вопросы клиенту.

Например:

```text
Уточните, пожалуйста, станцию назначения груза.
Уточните, пожалуйста, желаемый период перевозки (даты или месяц).
```

Если поле неоднозначно, вопрос содержит информацию о том, что именно система смогла обнаружить и почему этого недостаточно.

## Использование

### Обработка файла

```bash
python cli.py path/to/request.docx
```

Поддерживаются все форматы, перечисленные выше.

### Обработка без LLM
```bash
python cli.py path/to/request.txt --no-llm
```
### Обработка текста из stdin
```bash
echo "ООО АгроТранс. Ставрополь - Новороссийск. Пшеница, 20 вагонов, октябрь 2026." | python cli.py -
```
CLI выводит структурированный JSON в stdout.
Если заявка неполная, дополнительные вопросы клиенту выводятся в stderr.

## Использование LLM
LLM call отключается автоматически, если переменная окружения `GROQ_API_KEY` отсутствует.
Для включения:
```bash
# Windows PowerShell
$env:GROQ_API_KEY="your_api_key"

# Linux / macOS
export GROQ_API_KEY="your_api_key"
```
После этого pipeline автоматически использует дополнительный LLM-pass, если `--no-llm` не указан.
Текущая реализация использует модель:
```text
openai/gpt-oss-20b
```
через Groq/LangChain integration.

## Дизайн и ограничения

Это **прототип**, а не готовая production-система.

На что было обращено внимание:

* hallucinations: source-grounding constraint, модель не может использовать evidence, которого нет в исходном документе;
* explainability and determinism: засчёт rule-based;
* возможности работы без LLM;

При этом rule-based слой ограничен доменными словарями и regex. В частности, список станций не является полным справочником, поэтому неизвестные станции могут быть пропущены. LLM fallback частично компенсирует это ограничение, но не отменяет необходимости валидации результата.

Небольшая evaluation выборка также не позволяет делать выводы о production-level generalization.
